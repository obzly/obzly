Fixes for slow Logs insights and failing Web analytics on a large production project (about 150
million log lines a day), and safer API shutdowns.

## Highlights

- **Message patterns, version 2.** Generated IDs, names, emails, Kubernetes pod suffixes, JSON
  string values and `key=value` values no longer make a pattern each, and long messages are masked
  before they are cut, so where the cut falls no longer depends on the values before it. On the
  production project that prompted this release, five minutes of logs went from 42,900 patterns to
  13,400. A pattern the new rules don't change keeps its hash, so its history, sampling rules and
  saved filters carry on. Logs stored before the upgrade keep theirs; for a week, Patterns,
  Anomalies and log pattern alerts leave patterns that were regrouped out of *new* and *dropped*,
  and say so.
- **Smaller log rollups.** Each compacted segment gets two more rollups built from its per-minute
  counts: per minute without the message pattern, and per hour by level, service and pattern.
  Volume & noise, Patterns, Health map, histograms and deploy markers read the smallest one that
  answers. Without the pattern, a minute of that project is about 38 rows instead of 15,000.

## Fixes

- **Logs › Patterns and Volume & noise** took 150 to 170 seconds on the project above, right at
  the 170 second query limit: their 7 and 14 day counts read per-minute rollups that held a row
  per pattern and pod, and the patterns were nearly one per line.
- **Web analytics** hourly builds ran out of memory on every pass on the same project: a worker
  gives each search 1/16 of its memory (256 MB at 4 GiB), too little for a slice of an hour with
  multi-KB messages. An hour build now has its own budget (3/16 of the worker, 512 MB to 1 GB) and
  one thread.
- **API rollouts and scale-downs** cut Logs queries off: a stopping API pod gave in-flight requests
  10 seconds, while a query may run 170, so the control plane answered 502. A stopping replica now
  flushes its buffered logs first and then lets running queries finish, for up to 180 seconds by
  default (`SHUTDOWN_REQUEST_GRACE_SECONDS`); Live Tail reconnects to another replica. The Helm
  chart (0.7.3) and the HA manifests give API pods a 240 second termination grace period to match,
  and the chart's API autoscaler waits 10 minutes before removing a replica, one at a time.
- **API logs:** successful OTLP ingest calls and health checks log at debug (a busy Site's API pod
  logged about 1,150 a minute, rotating everything else out of its log within minutes); server
  errors log at warn.
- **Storage:** empty past months of the per-minute and per-hour rollup streams are now dropped like
  the others.

## Upgrading

Two new migrations, both additive. Upgrade the Sites, then the control plane. Workers build the new
rollups for existing segments in the background over a few hours; until a segment has them, its
queries read the per-minute rollups as before. If you deploy with your own manifests, raise the
API pods' `terminationGracePeriodSeconds` to 240 so running queries get their full 180 seconds.
Details:
[the upgrade runbook](https://github.com/obzly/obzly/blob/main/docs/runbooks/upgrade.md#releases-that-need-action).
